# mbd-toolchain-lab — 一个最小可用的 MBD（基于模型的设计）工具链

> 把 **MBD 的四个环节**用纯 Python 写一遍，并且**每一步都能验证**：
> **框图模型 → 定步长仿真 → C99 代码生成 → 模型与生成代码逐位比对**。
>
> 纯 **Python 标准库**，零第三方依赖。生成的是**标准 C99**，用 `gcc -std=c99 -Wall -Wextra -Werror` 编译无告警。

## 1. 为什么做这个

MBD 岗位的日常工作绕不开四件事，而它们恰好是"用过工具"和"知道工具在干什么"的分界线：

| 环节 | 说清楚它需要什么 |
|---|---|
| **模型设计** | 框图块之间**谁先算谁后算**（拓扑排序）、反馈环**靠什么打断**（状态块 vs 代数环）、状态更新**放在哪一步** |
| **仿真** | 定步长离散化的语义：输出反映的是"更新前"还是"更新后"的状态 —— 这一条错了，模型和代码就永远对不上 |
| **代码生成** | 模型怎么变成 C：状态怎么落到结构体、中间量怎么保证**运算顺序一致**、查表与状态机怎么落地 |
| **集成验证** | 生成代码与模型**是不是同一个东西** —— 判据应当是"逐位一致"，而不是"看着差不多" |

所以这个项目的目标不是"能生成代码"，而是三件事：

1. **算得对**：模型仿真结果要符合物理/工程关系（Buck 稳态占空比 = Vo/Vin、库仑计数 = 安时数）；
2. **对得上**：生成代码与模型**逐位一致（最大绝对误差 0.0）**，且这是**自动跑的 CI 断言**；
3. **说得清**：每个设计取舍（为什么状态更新放最后、为什么非直通块不取输入）都写在代码注释与本文档里。

## 2. 快速开始

```bash
# 全部演示：示例模型 / 仿真 / 代码生成 / 一致性校验
python -m mbd all

# 单独跑
python -m mbd lib      # 列出预置模型与拓扑序
python -m mbd sim      # 跑仿真并打印关键点
python -m mbd gen      # 打印生成出来的 C 代码
python -m mbd check    # 模型 ↔ 生成代码 一致性校验

# 单元测试
python -m unittest discover -s tests -t .
```

## 3. 目录结构

```

                    Abs / MinMax / Lookup1D / Integrator / UnitDelay / RateLimiter

mbd/codegen.py      模型 -> C99 代码生成（含查表函数与状态机）
mbd/library.py      预置示例模型：BMS 的 SOC 估算 / Buck 电压闭环 / 斜率限制跟踪器
mbd/__main__.py     四个演示的入口

tests/              86 项单元测试
```

### 执行顺序（**全项目最关键的一条口径**）

每一步按拓扑序做两件事：

1. **算输出** —— 直通块用本步输入；**非直通块（积分器 / 单位延时 / 速率限制 / 状态机）只用状态**；
2. **更新状态** —— 全部输出算完之后，再统一更新。

第 1 步里"非直通块不取输入"不是优化，而是**正确性问题**：它们的输入来源此刻可能还没算出来 ——
那正是它们能打断代数环的原因。第 2 步放在最后，是为了避免"同一步里先更新的块影响后算的块"，
否则结果会依赖块的书写顺序，代码生成也无法复现（生成代码里，这个顺序是**写死的**）。

## 4. 实测结果

### 4.1 预置示例模型（都取自 BMS / 电源控制方向）

```
buck_voltage_loop      dt=0.0001   块 11  连接 13  状态块 2  状态变量 3  Inport 1
    拓扑序：integ → vout → drop → vref → err → ki_term → kp_term → duty_raw → duty → drive → dv
rate_limited_tracker   dt=0.001    块  2  连接  1  状态块 1  状态变量 2  Inport 1
    拓扑序：cmd → ramp
soc_estimator          dt=1        块 10  连接 11  状态块 2  状态变量 4  Inport 2
    拓扑序：i_pack → coulomb_rate → mode → rest_gate → soc → v_pack → ocv_soc → ocv_err → corr → soc_rate
```

> 注意 `buck_voltage_loop` 的拓扑序里 **`integ` 与 `vout`（两个积分器）排在最前面** ——
> 它们的输出只依赖状态，不依赖任何本步输入，所以整条 PI + 被控对象的反馈环被它们打断，
> 排序能正常完成。若把积分器换成直通块，这里就会报**代数环**。

### 4.2 仿真：算出来的数符合物理关系

**Buck 电压闭环**（Vin=24 V，给定 12 V，后半程切 15 V，dt=0.1 ms，4000 步）：

| 时间(s) | 输出电压(V) | 占空比 | 误差(V) |
|---:|---:|---:|---:|
| 0.0000 | 0.00000 | 0.60000 | +12.00000 |
| 0.0100 | 13.56756 | 0.78823 | −1.56756 |
| 0.0500 | 12.05111 | 0.49894 | −0.05111 |
| 0.1000 | 11.99979 | 0.50001 | +0.00021 |
| 0.1999 | **12.00000** | **0.50000** | +0.00000 |
| 0.3999 | **15.00000** | **0.62500** | +0.00000 |

> 稳态占空比 **0.50000 = 12/24**、**0.62500 = 15/24** —— 正好是 Buck 的 `d = Vo/Vin`。
> 这不是"跑出来是多少就写多少"，而是**模型算出来的数必须满足的物理关系**，测试里有对应断言。

**BMS SOC 估算**（Q=50 Ah，SOC0=0.60，dt=1 s；2 A 放电 → 静置 → 3 A 充电 → 静置）：

| 时间(s) | SOC 估算 | 库仑+修正速率 | 状态机 | OCV 查表 SOC |
|---:|---:|---:|:--:|---:|
| 0 | 0.600000 | +3.389e−04 | 静置 | 0.7750 |
| 900 | 0.590350 | −1.111e−05 | 放电 | 0.7750 |
| 1439 | 0.584361 | −1.111e−05 | 放电 | 0.7750 |
| 2000 | 0.743044 | +1.539e−04 | 静置 | 0.8200 |
| 2879 | 0.776492 | +1.667e−05 | **充电** | 0.9500 |
| 3599 | 0.893540 | +7.292e−05 | 静置 | 0.9300 |

> **库仑计数可对账**：2 A × 1800 s = 1 Ah，占 50 Ah 的 **2%**，SOC 由 0.600 降到 0.584 —— 与理论一致。
> **OCV 修正在静置时才起作用**：带载时端电压被内阻拉低，直接用 OCV 查表会明显偏低，
> 所以模型只在静置状态下把 `K·(SOC_ocv − SOC)` 加进积分器 —— 这就是 SOX 算法里的常规做法。

**斜率限制器**：输入在第 10 步给阶跃 1.0，rise=10 /s、dt=1 ms（每步最多 0.01），
从第 10 步起每步走 0.01，**第 110 步正好到 1.0**。

### 4.3 ⭐ 模型 ↔ 生成代码：**逐位一致**

这是本项目最核心的一组结果。做法是：Python 跑一遍模型记下**每个块每一步**的输出，
再把生成的 C 代码编译、跑**完全相同的激励**、逐块逐步比对：

```
模型 buck_voltage_loop：11 个块，400 步，编译器 gcc
  模型 ↔ 生成代码 逐位一致（最大绝对误差 0.0）
模型 rate_limited_tracker：2 个块，400 步，编译器 gcc
  模型 ↔ 生成代码 逐位一致（最大绝对误差 0.0）
模型 soc_estimator：10 个块，400 步，编译器 gcc
  模型 ↔ 生成代码 逐位一致（最大绝对误差 0.0）

结论：全部逐位一致
```

**判据是"最大绝对误差 = 0.0"，不是"小于某个容差"。** 因为两边都是双精度、
运算顺序也刻意保持一致，任何非零偏差都说明**代码生成器写错了**，而不是"浮点误差"。

另外还有一组全块类型的模型（13 种块全用上 + 反馈环）也参与这条断言。

### 4.4 生成代码长什么样

以最简单的模型为例（`python -m mbd gen` 会打印完整结果）：

```c
/* ---- 第 1 步：按拓扑序算输出 ---- */
v_cmd = u[0];
v_ramp = s->ramp_y;

/* ---- 第 2 步：全部输出算完后统一更新状态 ---- */
s->ramp_y = s->ramp_y + fmin((10.0) * (0.001), fmax(-(10.0) * (0.001), (v_cmd) - s->ramp_y));

/* ---- 输出 ---- */
y[0] = v_cmd;
y[1] = v_ramp;
```

生成物包含：状态结构体、`<model>_init()`、`<model>_step(s, u, y)`、
`<model>_block_names[]`（用于比对时定位到具体块）、查表函数、状态机输出表。

> `y[i]` 的下标与模型拓扑序一致，所以**每一个中间量都能定位到具体块** ——
> 这也是 §4.3 能把误差精确报到"第几步、哪个块"的原因。

## 5. 开发中踩到并修掉的问题

| # | 现象 | 性质 | 根因与修复 |
|---|---|---|---|
| 1 | 仿真报 `KeyError: 'ki_term'` | **执行顺序错误** | `step()` 给**非直通块**也去取本步输入，而它们的输入来源那时还没算出来。改为：直通块在"算输出"阶段取输入，非直通块**只在"更新状态"阶段取** |
| 2 | 放电被状态机判成**充电** | **建模错误** | 状态机接的是电流的**绝对值**，放电（2 A）也满足"大于充电阈值"。改为接**带符号**电流，并加 `rest_enter` / `rest_exit` **双阈值迟滞**（否则零附近抖动会来回跳） |
| 3 | 电流正负方向与注释**相反** | **文档错误** | 注释写"正为充电"，而实现是 `d(soc)/dt = −I/(3600Q)`（正为放电）。统一成**正为放电**并写进 docstring |
| 4 | 三个状态里有**两个输出值相同** | **建模错误** | `charge` 与 `discharge` 都输出 0.0，从输出上分不出充放电。改为 0/1/2 三个互不相同的状态码，再用查表映射成"静置修正增益" |
| 5 | 生成代码编译报 `has no member named 'mode_out'` | **生成器错误** | 状态机输出表是**文件作用域静态数组**，表达式里却写了 `s->mode_out`。去掉 `s->` 前缀（`mode_st` 才是结构体成员） |
| 6 | 输入激励 `{0: 12.0}` 被当成"按步给值" | **API 歧义** | `_pick_inputs` 靠"值是不是 list"来区分三种写法，导致常量被误判。改为按**值的类型**显式分支，并在 docstring 里写清三种写法 |
| 7 | 生成器 `TypeError: not all arguments converted` | 低级错误 | 格式串占位符个数与参数个数不一致（查表函数那两行）—— 说明**生成器的字符串模板也要有测试覆盖**，后来补了结构层测试 |
| 8 | 两个测试断言写错（插值期望值、结构体字段空格） | **测试错误** | 50 落在段 `[5.001, 100]` 而不是 `[5, 100]`；生成时字段按 `%-7s` 对齐会有多个空格。**核对后改测试而不是改正确的实现** |

## 6. 边界说明（**请先读完这段再看结论**）

* **本项目是"按 MBD 的语义写一遍"的教学与自研实现，不是 Simulink / Embedded Coder 的替代品。**
  **没有也不可能有 MATLAB/Simulink 的模型文件格式兼容** —— 那种格式是闭源的。
  本项目覆盖的是 **模型 → 仿真 → 代码生成 → 一致性验证** 这条主链路的**语义与工程做法**。
* **代码生成是"逐块直译"**：不做定点化、不做表达式融合、不做查表优化、不做死代码消除，
  也**不生成符合 MISRA / AUTOSAR 的代码**。真实量产工具链会做这些。
* **求解器只有定步长前向欧拉**：没有变步长、没有刚性求解器、没有代数环迭代求解
  （遇到代数环是**显式报错**，不是想办法解出来）。
* **状态机是 Stateflow 的极小子集**：不支持层次状态、并行状态、`after`/`on` 事件、
  历史节点、内部转移与 entry/during/exit 动作。这些在真实项目里很常用，本项目**刻意不做半吊子**。
* **没有做定点 / 溢出 / 饱和的数值分析**，浮点一律双精度。
* **示例模型是示意性的，不是产品级模型**：
  * `buck_voltage_loop` 的被控对象是**一阶近似**，不含开关纹波、不含采样与 PWM 量化、不含延时；
  * `soc_estimator` 的 OCV–SOC 曲线是**典型形状的示例数据，不是实测电芯数据**，
    也不含温度修正、内阻模型、老化（SOH）耦合；
  * 两个模型的参数**没有按真实硬件整定过**。
* **没有硬件在环（HIL）**：本项目只做模型与生成代码之间的一致性（软件在环意义上的比对），
  不涉及目标板、不涉及实时性验证。

## 7. 下一步可做

1. 加**定点数类型**（`fixdt(1,16,12)` 这类）与溢出/饱和分析，让生成代码能直接上 MCU；
2. 加**代数环的迭代求解**（不动点迭代 + 收敛判据），而不是只报错；
3. 支持**层次子系统**与**模型引用**，让大模型能分块生成；
4. 加 **A2L / ASAP2 标定量描述文件**导出，把标定接口也打通；
5. 把状态机补成**层次 + 事件**的版本。
